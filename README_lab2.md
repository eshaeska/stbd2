# Лабораторна 2. NoSQL. Система управління автопарком

СУБД: **MongoDB** (документна) — основна NoSQL; **Redis** (key-value) — друга NoSQL іншого типу; **PostgreSQL** — SQL-еквівалент.

## 1. Види NoSQL баз

| Тип | Модель даних | Приклади | Коли доречна |
|---|---|---|---|
| Key-Value | ключ → значення | Redis, Memcached, DynamoDB | кеш, сесії, лічильники, "живий" стан, TTL |
| Документна | JSON/BSON-документи з гнучкою структурою | MongoDB, CouchDB | різнорідні дані, вкладені об'єкти, журнали подій, каталоги |
| Стовпчикова (wide-column) | сімейства стовпців, розподілене сховище | Cassandra, HBase | дуже великі обсяги запису, розподілені системи |
| Графова | вершини та ребра | Neo4j, ArangoDB | зв'язки: маршрути, рекомендації, соцмережі |
| Time-series | значення за часом | InfluxDB, TimescaleDB | метрики, IoT, датчики |
| Пошукова | інвертований індекс | Elasticsearch | повнотекстовий пошук, логи |

## 2. Чи доцільно виносити частину даних з SQL?

**Так — телеметрію авто** (GPS-координати, швидкість, рівень пального, показники двигуна, коди помилок DTC), що надходить від бортових пристроїв.

Аргументи **за** (документна БД):
1. **Обсяг і швидкість запису.** Одне авто шле повідомлення кожні 5–30 с → мільйони записів на місяць. Записи тільки додаються (append-only), майже не змінюються.
2. **Різнорідна структура.** Різні моделі пристроїв передають різні набори датчиків (є/немає дані двигуна, масив кодів помилок різної довжини; для електромобілів з'являться дані батареї). У SQL це або NULL-колонки, або нові таблиці/міграції, у документній БД — просто інші поля.
3. **Читання "цілим документом".** Типовий запит — "останні N повідомлень авто з усіма показниками". У MongoDB це один документ, у SQL — JOIN трьох таблиць.
4. **Немає складних зв'язків і транзакцій між записами.** Телеметрія не потребує ACID-звʼязків з іншими таблицями.
5. **Масштабування.** Шардування за `vehicle_id`, TTL-індекс для автоматичного видалення старих даних, вбудовані гео-запити (`2dsphere`).

Аргументи **проти** / що лишається в SQL:
- Довідники, рейси, водії, штрафи, страхування, обслуговування — це реляційні, транзакційні дані з FK, `soft delete` і аудитом (лаба 1) → **лишаються в PostgreSQL**.
- Недоліки гібриду: немає FK між `telemetry.vehicle_id` і `vehicles` (цілісність на рівні застосунку), два джерела даних, JOIN між БД робиться в коді.

**Redis (інший тип):** "живий" стан автопарку — остання позиція авто, статус "онлайн" (TTL), гео-пошук найближчого авто, лічильники, топ водіїв. Дані малі, потрібен мікросекундний доступ і автоматичне зникнення застарілого стану.

## 3. Модель у MongoDB (колекція `telemetry`)

```json
{
  "vehicle_id": 17,
  "ts": ISODate("2026-01-01T08:00:30Z"),
  "location": { "type": "Point", "coordinates": [30.52, 50.45] },
  "speed_kmh": 62.5,
  "fuel_level_pct": 71.2,
  "engine": { "rpm": 2100, "coolant_temp_c": 92.5, "load_pct": 40 },   // необов'язково
  "dtc_codes": ["P0300", "P0171"]                                      // необов'язково
}
```
Індекси: `{vehicle_id:1, ts:-1}`, `{dtc_codes:1}` (multikey), `{location:"2dsphere"}` (у `mongo_setup.js`).
Файл: `mongo_setup.js` (валідація `$jsonSchema`, індекси, CRUD, агрегація, гео-запит).

## 4. Еквівалент у SQL (PostgreSQL) — файл `04_telemetry_sql.sql`

Один документ → 3 таблиці:

| MongoDB | PostgreSQL | Звʼязок |
|---|---|---|
| поля верхнього рівня + `location` | `telemetry_points` | 1 |
| вкладений об'єкт `engine` | `telemetry_engine` (PK = FK `point_id`) | 0..1 |
| масив `dtc_codes` | `telemetry_dtc` (`point_id`, `dtc_code`) | 0..N |

Також: індекси `(vehicle_id, ts DESC)`, `dtc_code`, `point_id`; view `vw_telemetry_full` (збирає "документ"), функція `sp_telemetry_add`.

## 5. Тестування швидкодії (`Fleet.Bench`)

### Методика
- **Дані:** 100 авто × 5 000 повідомлень = **500 000** документів (≈ 1,7 доби роботи з кроком 30 с). Генерація детермінована (seed) → в обидві БД потрапляють **ідентичні** дані. ~10 % повідомлень без даних двигуна, ~3 % з кодом помилки.
- **Однакові умови:** однакові за змістом індекси; без FK на `vehicle_id` (у Mongo їх немає); однакові параметри запитів (одні й ті самі авто/вікна часу); результат читається повністю (усі колонки/поля), а не лише відкривається курсор.
- **Прогрів і повтори:** 3 прогрівальні запуски (не враховуються), далі 30 вимірювань (для важкої агрегації — 5). Показуємо **медіану** і **p95** (середнє спотворюють викиди). Кеш "гарячий" (типовий режим роботи сервера).
- **Що вимірюється і чому:**

| Тест | Навіщо |
|---|---|
| Масове завантаження 500 тис. (Mongo `InsertMany`; PG бінарний `COPY`) | початкове наповнення/міграція; кожна БД — найшвидшим штатним способом |
| Побудова індексів | вартість індексації після завантаження |
| Одиничний INSERT | реальний сценарій: пристрій шле 1 повідомлення (у PG — 1–3 INSERT в одному батчі/транзакції) |
| Останні 50 повідомлень авто | головний сценарій читання; у PG потрібен JOIN 3 таблиць |
| Діапазон 6 год для авто (~720 записів) | історія/звіт за період |
| Агрегація по всьому набору | аналітика; тут SQL традиційно сильний |
| Пошук за кодом помилки P0300 | запит за елементом масиву (multikey) vs JOIN з окремою таблицею |
| Розмір на диску | вартість зберігання (дані + індекси) |

- **Гіпотези до запуску** (перевіряються результатами, не підганяються): запити, що читають повний запис, швидші в MongoDB (немає JOIN); агрегація й масове завантаження можуть бути на боці PostgreSQL. Якщо результат інший — пояснити причину.

### Результати
Вставити сюди вміст `results.md`, що створює програма після запуску, і додати висновки (де що швидше та чому).

- Налаштування обох СУБД за замовчуванням.

## Запуск

1. Запустити MongoDB (порт 27017) і Redis (порт 6379), PostgreSQL з базою `fleet`.
2. У `Fleet.Bench/Program.cs` вказати свій пароль PostgreSQL (`PgCs`).
3. `cd Fleet.Bench` → `dotnet run` (бенчмарк, ~1–3 хв) або `dotnet run -- redis`.
4. Бенчмарк сам перестворює `telemetry_*` у PostgreSQL і колекцію `telemetry` у MongoDB.

## Питання, які можуть поставити на захисті

- **Чому так мало даних?** 500 тис. вистачає, щоб індекси й JOIN-и мали значення і щоб дані не вміщались у "один блок"; параметр масштабується; тест показує тенденцію, а не абсолютні цифри.
- **Чому такі запити?** Це три типові сценарії телеметрії: останні події, звіт за період, аналітика + пошук за кодом помилки.
- **Чому PG завантажується через COPY, а не INSERT?** Щоб порівнювати найшвидші штатні способи кожної БД, а не "погано налаштований" варіант.
- **Чому немає FK на `vehicle_id`?** У документної БД FK немає; щоб тест був чесним. У гібриді цілісність забезпечує застосунок.
- **Чому не time-series БД?** Тип залишено за студентом; MongoDB обрано через різнорідну структуру і документну модель; для чистих метрик доречніші TimescaleDB/InfluxDB.
- **Коли SQL краще?** Транзакції, звʼязки, звіти по кількох сутностях, суворі обмеження цілісності (лаба 1).
- **Чому Redis, а не Mongo, для "останньої позиції"?** Потрібен доступ за ключем за мікросекунди, TTL і гео-пошук у памʼяті; історія не потрібна.
